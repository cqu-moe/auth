# Administrator account recovery

`POST /api/v1/auth/admin/reset-authentication` accepts `{ userId }`. It requires the existing `user:set-password` authority (currently `superAdmin`), a live strong-authenticated administrator session, and an `admin` purpose proof from the last five minutes. The transaction rechecks the current role, ban status, session expiry and both proofs after password hashing. An ordinary administrator cannot perform recovery. The existing hierarchy permits superAdmin to recover another administrator, including superAdmin.

A successful response is `{ status: true, password }`. The 32-character password comes from Better Auth's cryptographic generator and is hashed by the configured native password hasher. The plaintext exists only in the current response and the administrator's result dialog; it is not saved in the database or audit. The dialog clears it on close. There is no password retrieval endpoint, recovery session, approval workflow or forced password change. A fresh retry performs a new complete reset and produces a different password.

Migration `0012_account_recovery.sql` adds a reset revision, verification ownership and a recovery audit table. The reset transaction replaces the credential-account password, disables and deletes TOTP/recovery codes, deletes all Passkeys, interactive sessions, OAuth access/refresh credentials, trusted-device records, and attributable outstanding authentication/reset/authorization challenges. Audit records contain actor, target, outcome and time, never credentials. A batch failure rolls back the entire change and returns no password. School binding, entitlements, service clients and private Worker RPC remain intact. A recovered administrator can sign in normally with the new password but must configure and complete strong authentication before using management functions again.

## Concurrent authentication

Deleting existing credentials alone is insufficient: an old password or Passkey verification may already be running. `auth-reset-revision.ts` captures the revision before the request's first authentication database read. The same Request retains it across nested `createAuth` calls; the public-origin forwarding Request inherits it. Every native Auth mutation runs in one D1 batch with a revision assertion. Recovery increments that revision in the same transaction as the complete reset. A stale mutation therefore either committed before recovery and is cleared by it, or fails without committing after recovery. This covers native factors, anonymous Passkey login, session creation, proof storage and the four password-free Passkey account operations.

This is deliberately one global revision rather than a second per-user credential framework. An unrelated authentication request with a write that crosses the rare recovery transaction must retry; a new request succeeds. Other users' existing sessions and challenges are retained. Business reads and private RPC use the original database, not this Auth-only facade. There is no KV, Durable Object lock or interactive transaction. Auth SQL must use the configured adapter; new credential writes must not bypass the facade. Unsupported unprepared writes/raw mutations fail closed.

Current native change-email OTP identifiers combine two email addresses with an ambiguous delimiter. Their verification records now carry server-assigned `authUserId`; completion requires that owner, and recovery deletes that owner's challenges. Legacy unowned change-email challenges must be requested again after rollout. Plaintext user IDs, native JSON ownership and exact single-email OTP identifiers cover other legacy pending records. Anonymous Passkey challenges without an owner may remain until expiry: deleted keys and the write fence prevent their reuse. The legacy stateless `/verify-email` endpoint remains disabled.

The native `/admin/set-user-password` endpoint retains its existing password-only meaning and recent-strong gate. The management UI uses the full recovery endpoint above.

## Verification

`test/do/admin-recovery.do.test.ts` uses actual HTTP, D1, password hashing, TOTP, recovery codes, signed WebAuthn and native OAuth issuance. Deterministic barriers pause the real D1 write before committing, then perform recovery and resume it. Coverage includes old password/Passkey/TOTP/recovery-code logins, pending Passkey enrollment, all four UV Passkey account operations, pending reset/OAuth codes, device tokens, rollback, administrator authority changes and the unrelated-user retry. Real Worker RPC authorization uses a hashed service secret before and after recovery. UI tests exercise confirmation, authentication cancellation, and clearing the one-time result.

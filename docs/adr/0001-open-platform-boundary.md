# Auth 与统一 API/MCP 平台分别承担身份授权和业务接入

Auth 延续中央登录、应用注册与授权中心的职责；未来统一 API/MCP 平台接入各子平台的开放能力。**本次只在 Auth 架构设计中预留授权与集成边界，不建设 API/MCP 平台或新增对外业务端点。** 域名、部署形态、业务工具清单和完整资源划分留到平台启动时决定。

未来平台首批对外能力限于只读业务结果，不向普通第三方交出学校登录票据、Cookie 或密码。现有 QuickLogin 的学校登录能力作为单独审批的高信任能力；具体授权和迁移方式尚未确定。

未来首期第三方应用由管理员注册、审批，优先适配明确要支持的 MCP 客户端，不先建设开放应用注册平台。本次只记录该策略，不实施第三方接入平台、MCP 客户端适配或动态注册能力。

预留的设计约束是区分客户端、用户、目标资源与权限，保留业务服务自身的授权职责，让未来 API/MCP 能消费同一套身份与授权契约。无需为此提前新增网关、MCP Worker、占位路由或未使用的通用抽象。

# Optional DPoP

Auth 1.7 uses the provider's native RFC 9449 proof support. Existing clients remain Bearer clients. Sending a valid DPoP proof to the token endpoint opts that grant into sender-constrained tokens; authorization still requires S256 PKCE. Clients may additionally send `dpop_jkt` on authorization. Administrators can set `dpop_bound_access_tokens: true` on the existing client create/PATCH API to require proofs for that client. The default is false. Native resource policy supports `dpopBoundAccessTokensRequired`; the current single Auth resource remains optional. Future API/MCP resources must explicitly configure their audience and per-client resource policy before being introduced.

Use a standard client such as oauth4webapi: create a DPoP handle with an ES256 key pair, pass it to code exchange, refresh and protected-resource requests. The response reports `token_type: DPoP`; protected requests use `Authorization: DPoP <access_token>` plus a new `DPoP` proof on every request. Refresh must use the original key, including after refresh-token rotation. Persist the private key securely alongside the grant (browser non-exportable WebCrypto/IndexedDB, backend protected key storage); do not regenerate it on every process start. Losing the key requires a fresh login/authorization. PKCE, current account/client status, scopes, application entitlements and QuickLogin grant checks still apply. DPoP is neither MFA nor a replacement for business authorization.

The resource helper verifies the JWT locally against Auth's JWKS and invokes native `enforceDpopBinding` with the complete Request and `createDpopReplayStore(internalAdapter)`. This composition avoids an outbound self-fetch: the upstream request verifier currently only accepts a remote JWKS URL. The token-only compatibility helper explicitly rejects `cnf.jkt`. Both helper paths preserve current user/client/session authority. Native userinfo performs the proof check itself; its custom claims callback checks current authority only after native validation, so the same proof is not reserved twice. Resource routes must authenticate before rewriting a Request; pass the original public method/URL, never reconstruct them from user-supplied Forwarded headers. Current device and service-ticket routes retain their original Request. The Auth provider boundary normalizes scheme/host to `BETTER_AUTH_URL` while retaining the public route path, allowing internal origin forwarding without treating arbitrary forwarded headers as authoritative. A proxy that changes paths must restore the actual public path at its trusted boundary.

AS and RS reserve proof identifiers atomically in the existing D1 verification table. Deterministic primary keys reject simultaneous replays across fresh Worker contexts. Native verification lookup cleanup removes expired rows; normal authorization/verification traffic triggers that cleanup. DPoP keys and proofs are never application telemetry: structured DPoP headers and labeled proof/token strings are redacted. No nonce service, custom SDK, KV or mandatory client migration is introduced.

Validation uses actual OAuth code/refresh endpoints, real D1, concurrent proof requests, QuickLogin registration HTTP, and oauth4webapi. It includes the internal-origin/public-proof boundary, same-key refresh, wrong-key refresh rejection, Bearer downgrade rejection, and ordinary Bearer compatibility through the existing OAuth/QuickLogin suite.

# Auth 安全与第一方接入升级

日期：2026-10-09。状态：正式规格；HTTP、Worker RPC 测试边界及 GitHub Issues 发布位置已由用户确认。本文描述目标行为，不代表已实现、测试通过或上线。

## Problem Statement

CQU 身份与授权中心需要在保留现有账号、学校绑定、业务权益和后台课表同步的前提下，升级认证框架并收紧安全边界。现有第一方浏览器接入依赖根域共享 Cookie，中央会话与应用会话隔离不足；会话、临时验证数据和限流同时依赖 KV 与 D1，撤销和并发行为较难保证。

用户还需要更明确的账号安全规则：敏感操作应验证实际认证强度；邮箱找回不能绕过已有二次验证；Passkey 应真正完成用户验证；退出、改密、人工恢复与后台同步必须有清楚且不同的生命周期。OAuth 升级应采用 S256 PKCE，并提供可选 DPoP，不能把“库支持某项能力”当成系统已完成接入。

本次改造同时要保持结构简单。第一方后台已有私有 Worker RPC，不应为统一形式而把后台同步改造成逐用户 refresh token 系统。未来统一 API/MCP 平台只预留身份和授权契约，本次不建设平台。

## Solution

升级 Better Auth，使用 D1 承担 Auth 的权威会话、验证数据及数据库限流，移除 KV 依赖。第一方 Web 经中央 OAuth/OIDC 登录建立各自独立的应用会话；后台 Worker 继续通过私有 Service Binding RPC 使用受限服务身份。

为现有账号增加可选 Passkey，保留密码和注册流程。集中实施近期认证、管理员强认证、账号恢复和设备撤销策略，覆盖业务接口及对应的框架原生端点。OAuth 授权码流程强制 S256 PKCE，DPoP 由客户端选择启用，但启用后的密钥绑定、防重放和禁止降级必须完整有效。

所有第一方应用默认向用户开放，无需用户单独开通或授权，也不提供用户停用第一方授权的开关。管理员通过业务权益控制用户是否能使用相应应用，以及可用功能和额度。退出设备、改密和账号恢复都保留已启用的后台课表同步；账号封禁、学校解绑或服务身份被管理员禁用时，停止对应访问。

## User Stories

### 登录与第一方应用

1. 作为普通用户，我希望升级后保留中央账号、学校绑定和业务权益，从而不必重新建立业务资料。
2. 作为普通用户，我希望继续使用密码登录和现有注册流程，从而不被强制切换到新登录方式。
3. 作为普通用户，我希望中央登录后能进入第一方应用而无需反复输入密码，从而保留统一登录体验。
4. 作为普通用户，我希望各第一方网站持有独立的应用会话，从而单个网站的会话不能直接用于中央账号或其他网站。
5. 作为普通用户，我希望所有第一方应用默认向我开放，无需逐个开通或授权，从而直接使用第一方产品。
6. 作为具备权益管理权限的管理员，我希望通过业务权益控制用户是否能使用相应第一方应用，以及可用功能和额度，从而落实平台的使用规则。
7. 作为普通用户，我希望单站退出只结束该站会话，并停留在已退出页面，从而不会立即被自动登录回来。
8. 作为普通用户，我希望主动再次登录时可以复用中央登录状态，从而无需无意义地重新输入凭据。
9. 作为普通用户，我希望退出全部设备后，各应用及插件的设备访问都失效，从而不必逐站操作。
10. 作为普通用户，我希望漏收退出通知的应用也能在约定期限内停止访问，从而退出效果不依赖一次消息是否送达。

### Passkey 与近期认证

11. 作为普通用户，我希望给现有账号添加多个 Passkey，从而可以使用不同设备登录并降低单设备丢失的影响。
12. 作为普通用户，我希望经指纹、人脸或设备 PIN 验证的 Passkey 能独立完成登录，从而无需再输入密码或 TOTP。
13. 作为普通用户，我希望服务端确认 Passkey 已完成用户验证，从而仅触碰安全密钥或伪造客户端结果不能获得同等认证强度。
14. 作为普通用户，我希望五分钟内真实完成的认证能用于敏感操作，从而不必对连续操作反复验证。
15. 作为普通用户，我希望超过五分钟、错误会话或其他账号的认证证明不能使用，从而敏感操作始终对应当前身份。
16. 作为普通用户，我希望修改密码、更换邮箱、关闭或替换二次验证、管理恢复码以及添加或删除 Passkey 都受到统一验证保护，从而被窃取的普通会话不能直接修改永久登录方式。
17. 作为启用二次验证的用户，我希望密码路径仍要求 TOTP 或恢复码，从而密码泄露不会绕过我设置的二次验证。
18. 作为尚未启用二次验证的普通用户，我希望能通过现有认证方式完成安全设置，从而不会被要求提供尚未绑定的因子。
19. 作为使用信任设备的用户，我希望登录便利不会被当成刚完成强认证，从而敏感操作仍需要有效的近期验证。
20. 作为普通用户，我希望直接请求底层认证端点时也执行相同规则，从而安全性不取决于是否使用官方页面。

### 邮箱、管理与恢复

21. 作为普通用户，我希望邮箱验证码只用于适当的邮箱验证及密码找回，从而它不能代替已有的第二因子或直接获得越级登录。
22. 作为绑定学校账号的用户，我希望学校 CQU 邮件验证码处理继续工作，从而 Auth 自身的策略调整不会中断学校登录。
23. 作为管理员，我希望使用管理功能前必须完成 UV Passkey 或密码加 TOTP/恢复码，从而仅凭密码或角色信息不能进入管理功能。
24. 作为尚未配置强认证的管理员，我希望能先进入自己的安全设置完成绑定，从而不会因新策略陷入无法自助配置的状态。
25. 作为普通用户，我希望丢失二次验证时优先使用恢复码，从而能自行恢复访问。
26. 作为丢失全部二次验证材料的用户，我希望管理员能重置我的全部旧认证方式并提供随机新密码，从而恢复登录。
27. 作为人工恢复后的用户，我希望旧密码、Passkey、TOTP、恢复码、信任设备、旧设备访问及未完成的旧认证流程全部失效，从而旧凭据持有者不能重新进入账号。
28. 作为普通忘记密码的用户，我希望已有 Passkey 和二次验证仍然保留，从而密码找回不降低账号原有保护。
29. 作为人工恢复后的普通用户，我希望直接用随机新密码正常登录，再按需设置 Passkey 或二次验证，从而无需经过额外恢复流程。
30. 作为管理员，我希望在权限和强认证校验通过后一次完成重置并取得随机新密码，从而能够交付用户，且操作可审计而密码不进入日志。

### 撤销与后台业务

31. 作为普通用户，我希望正常改密后其他设备访问失效，当前已验证会话可以继续使用，从而控制账号访问而不打断当前操作。
32. 作为普通用户，我希望密码找回后旧设备凭据失效并重新登录，从而旧密码持有者不能继续沿用既有设备访问。
33. 作为使用后台课表同步的用户，我希望退出全部设备、正常改密、密码找回和人工恢复都不停止既有同步，从而业务连续性不依赖设备登录。
34. 作为普通用户，我希望学校解绑后停止相关学校访问与同步，从而解绑具有实际效果。
35. 作为管理员，我希望账号封禁后拒绝对应用户的交互访问与后台调用，从而后台通道不绕过封禁。
36. 作为管理员，我希望禁用应用后其 OAuth 与 RPC 能力停止工作，从而可控制受损或退役的应用。
37. 作为普通用户，我希望普通受保护读取最迟在撤销后六十秒失效，敏感账号操作和学校登录能力在下一次请求检查最新状态，从而撤销有明确时效。

### OAuth 与 DPoP

38. 作为 OAuth 客户端开发者，我希望授权码流程强制 S256 PKCE、严格回调匹配及事务绑定，从而被截获或篡改的授权码不能被随意兑换。
39. 作为 OAuth 客户端开发者，我希望升级后中央 issuer 身份与正式 discovery 契约保持连续，从而不会因接口路径与 issuer 混淆而接入失败。
40. 作为现有客户端开发者，我希望未启用 DPoP 的合法 Bearer 流程继续工作，从而本次升级不强制我先完成 DPoP 迁移。
41. 作为选择 DPoP 的客户端开发者，我希望签发、刷新和资源访问都绑定同一客户端密钥，从而被盗令牌不能脱离该密钥使用。
42. 作为选择 DPoP 的客户端开发者，我希望缺失 proof、错误密钥、错误请求绑定、重复 proof 或降级成 Bearer 都被拒绝，从而可选支持不会变成可绕过的保护。
43. 作为客户端开发者，我希望 scope、audience、应用状态及用户权限仍被校验，从而 DPoP 不取代正常授权规则。
44. 作为平台维护者，我希望 DPoP 重放检查覆盖多个 Worker 实例，从而并发请求不能利用进程内缓存的隔离重复通过。

### 私有 RPC 与运维

45. 作为第一方后台开发者，我希望继续通过私有 Worker RPC 使用服务身份和目标用户，从而无需为既有同步维护逐用户 refresh token。
46. 作为第一方后台开发者，我希望服务身份仅用于获批的 RPC 业务操作，从而不被当作用户的通用登录身份。
47. 作为普通用户，我希望 Auth 对 RPC 统一检查调用方权限、用户状态、必要权益和学校绑定，从而安全边界不只依赖调用方自觉遵守。
48. 作为平台维护者，我希望公网接口不能无条件转发任意用户标识来借用后台权限，从而私有能力不会间接变成公开的代用户接口。
49. 作为平台维护者，我希望会话、验证数据和限流由 D1 及框架原生能力支撑，从而减少状态同步和自建基础设施。
50. 作为平台维护者，我希望并发验证码消费、授权码兑换、恢复码使用及限流具有经过验证的行为，从而数据存储切换不会掩盖竞态。
51. 作为平台维护者，我希望过期验证和重放记录得到清理，从而短期安全数据不会无限积累。
52. 作为平台维护者，我希望升级保留账号、绑定、权益及必要的客户端数据，从而可接受的重新登录不会变成业务资料丢失。
53. 作为第一方接入方，我希望在中央 Cookie 切换前收到明确契约并完成适配，从而不会因单方面部署而失去登录能力。
54. 作为平台维护者，我希望未来 API/MCP 可以复用客户端、用户、资源和权限概念，从而届时能够扩展而无需现在提前建设平台。

## Implementation Decisions

### 架构与范围

- Auth 继续承担中央身份、交互登录、应用身份、OAuth 和账号安全职责。第一方应用后端管理本站会话；后台通过现有私有 Worker RPC 调用业务能力。
- 用户 OAuth 与第一方服务身份并存。服务身份只用于私有 RPC，不能修改中央账号安全设置或获取用户的通用登录身份；不新增等价的公网服务身份代用户接口。
- 所有第一方应用默认向用户开放，在平台给予该应用的权限范围内自动授权，不要求用户逐个开通、同意或重新启用。管理员通过业务权益控制用户是否能使用及其功能、额度，沿用现有权益管理权限层级；对象归属、应用权限和当前状态检查仍需执行。
- 保留现有 CQU/QuickLogin 会话协调及必要的 Durable Objects，不新增通用认证缓存、独立授权服务、客户端 SDK 框架或后台逐用户令牌体系。

### 框架与数据迁移

- 升级 Better Auth 及相关前后端包，连同 OAuth Provider、Passkey 和 Cloudflare 适配器一起验证兼容性。研究基线是 1.7.7；实施前核对当时可用的稳定版本和变化，不将旧研究版本误当永久最新版本。
- 移除 KV secondary storage；会话和 verification 使用 D1，关闭会话 cookie cache。限流必须显式使用数据库存储并补齐相应 schema，不能静默变成无效存储或实例内限流。
- Auth 运行时使用 native D1 对接框架内置适配器，业务数据仍保留现有查询方式；不为本次改造更换整套 ORM。
- 沿用项目的手写、顺序 SQL 迁移流程。框架 schema 输出可作为审查依据，不能直接重建已有迁移基线、自动覆盖全库或在生产执行未经审查的迁移。
- 核对 OAuth 客户端新字段、资源模型、Passkey 表、限流表、DPoP confirmation/replay 和近期认证所需的最少状态。复用原生表和原子操作；额外状态须有真实业务用途，不能为测试增加生产接口。
- 账号标识、学校绑定、业务权益和既有必要客户端数据必须保留。KV 中未完成的临时流程允许重启；部分用户可以重新登录或让插件重新连接。

### 第一方登录与撤销

- 中央登录 Cookie 限于 auth.cqu.moe；各应用使用独立的 host-only、Secure、HttpOnly 会话 Cookie。OAuth 交换和长期凭据留在既有后端，浏览器不持有长期 refresh token，不为此单独部署新 BFF 服务。
- 收紧可信来源，保持 Cookie 写操作的来源与 CSRF 防护；不能把同主域或 host-only 当作完整 CSRF 防线。
- 单站退出只结束本站会话，保留中央和其他站点登录，停留在已退出页面；仅在用户主动登录后重新接回。
- 全设备退出撤销中央与各应用的设备访问，包括仍可续发访问令牌的设备凭据。框架对 offline_access 的默认保留不能成为设备撤销的例外。
- 应用会话须关联可核查的中央登录或授权状态。退出通知可以加速，但漏收通知仍须满足撤销时限；权威验证不可用时，不能无限沿用旧允许结果，敏感操作不得失败放行。
- 普通读取最多允许六十秒撤销延迟；敏感账号操作和学校登录能力在下一次请求读取最新权威状态。六十秒是上限，不要求新增缓存。
- 单纯 JWT 验签或验证 DPoP 不构成当前授权状态检查，必须同时处理撤销、用户与应用状态及业务权限。

| 事件 | 设备与交互访问 | 第一方后台同步 |
| --- | --- | --- |
| 单站退出 | 结束本站会话；其他站点与中央登录保留 | 继续 |
| 退出全部设备 | 所有相关设备会话及续发能力失效 | 继续 |
| 正常改密 | 当前已验证会话保留，其他设备访问失效 | 继续 |
| 普通密码找回 | 旧设备访问失效；原 Passkey 与二次验证保留，重新登录仍须满足它们 | 继续 |
| 人工恢复 | 旧密码、Passkey、TOTP、恢复码、信任设备及旧交互凭据全部失效；生成随机新密码，用户正常登录 | 继续 |
| 用户封禁 | 拒绝该用户的交互访问 | 拒绝该用户后续调用 |
| 学校解绑 | 拒绝对应学校能力，不删除中央账号 | 停止对应同步 |
| 管理员禁用应用 | 拒绝该应用的访问 | 拒绝对应服务身份 |

- 撤销阻止后续访问，不承诺撤回已返回的数据。长任务在下一个可控制执行点检查停止条件，并阻止后续新工作，不另建通用任务取消平台。

### 认证强度、Passkey 与人工恢复

- Passkey 是现有账号的可选方式，支持多凭据，保留密码和现有注册流程。本轮不增加完全无密码的注册或账号模型。
- Passkey 仪式限定在中央认证站，固定 rpID 与 origin。密码学验证和凭据管理优先使用官方插件；服务端必须确认用户验证 UV，不能仅依赖注册选项、客户端界面或触碰安全密钥。
- 经 UV 的 Passkey 可独立完成登录及敏感操作所需的强认证，无需额外密码或 TOTP。密码路径按账号已启用的二次验证要求处理，未绑定因子的普通用户不被要求提供不存在的因子。
- 近期认证证明在服务端关联当前用户、当前会话、用途和五分钟有效期；挑战一次性消费。不把会话创建时间、自动续期或三十天信任设备当作刚完成强认证。
- 普通 Passkey 登录与当前会话再次验证是不同操作。再次验证不能接受另一个账号的 Passkey，不能通过偷偷切换登录身份满足原账号的敏感操作。
- 改密、换邮箱、关闭或替换 MFA、恢复码管理、添加和删除 Passkey 使用统一后端门禁；直接调用框架原生端点与应用封装端点都要受到保护。
- 管理员和超级管理员访问管理功能需具备 UV Passkey，或密码加 TOTP/恢复码的强认证依据。尚未配置者可访问自己的安全设置完成绑定；管理功能准入与敏感操作的五分钟要求分别判断。
- 取消 Auth 邮箱验证码作为第二因子的替代路径；保留邮箱验证与密码找回，但它们不能自动解除已有二次验证或越级建立完整登录。
- 学校 CQU 邮件验证码处理属于另一个认证域，继续保留，不随 Auth 邮箱第二因子取消而删除。
- 丢失二次验证先使用恢复码；材料全部丢失时，由具备对应管理权限的管理员完成强认证后执行一次人工重置。沿用现有管理权限层级，记录操作者、目标和结果；不建设额外的身份材料审核或审批工作流。
- 人工重置作废中央账号的旧密码、全部 Passkey、TOTP、恢复码、信任设备、旧交互会话、设备访问凭据及尚未完成的旧认证/重置流程，然后用密码学安全随机源生成新密码。系统仅保存密码哈希，在重置结果中一次性返回新密码供管理员交付，不写入日志或审计正文。成功响应必须表示旧认证已失效且新密码已生效，不能把部分完成报告为成功。
- 用户直接用随机新密码走正常登录，之后按需配置 Passkey 或二次验证；不增加受限恢复会话、强制重建因子或强制首次改密流程。被重置的管理员账号仍须完成既定强认证配置后才能使用管理功能。学校绑定、业务权益和私有 RPC 后台同步保留。

### OAuth 与可选 DPoP

- 用户授权码流程强制 S256 PKCE，验证回调地址、登录事务、issuer、audience 和权限。免同意不意味着免去协议校验；第一方身份、是否能保密和后台 RPC 权限分别建模。
- 保持中央 issuer 身份与必要签名材料连续；采用新版本资源模型表达当前实际存在的能力，不提前创建未来 API/MCP 的端点或资源清单。
- DPoP 可选，不强制任何现有客户端启用。合法未绑定 Bearer 继续验证；选择 DPoP 后，签发、刷新及资源请求必须持续证明持有绑定密钥，禁止降级。
- 资源端使用按真实请求验证的框架接口，覆盖 proof 签名、密钥、方法、公开目标 URL、时间、唯一标识、令牌哈希及 token 的正常授权要求。内部路由重写不能破坏或削弱公开 URL 校验。
- DPoP 重放检查必须使用跨实例原子存储。优先复用框架 replay store 和 D1 verification 的确定性主键占位，不以进程内 Map 作为唯一防线。
- DPoP 密钥与 Passkey 不共用，不要求用户每次请求进行生物识别。选择启用的客户端自行使用标准 OAuth 实现处理密钥持久化和丢失后的重新登录；本次不全面迁移所有客户端。
- 本轮不实现独立的服务端 nonce 挑战设施。DPoP 不替代 TLS、scope/audience、撤销、客户端身份或近期认证，也不宣称保护已经能够使用客户端签名密钥的攻击场景。

### RPC、部署与兼容性

- 复用现有服务身份及凭据验证，按具体 RPC 业务操作校验授权，不能仅信任 caller 提交的 clientId 或拥有 binding 这一事实。
- Auth 统一检查调用方状态和权限，以及目标用户状态、方法实际需要的权益和学校绑定；不向无需学校绑定的方法附加无关条件。
- 保留现有 CQU 会话控制、目标主机校验、限流和审计入口。通用采集能力不能因为处于私有 RPC 就跳过业务权限检查。
- 第一方接入方适配是中央 Cookie 切换的前置条件。先完成调用方清单和契约迁移，再切换 Cookie、清理旧根域 Cookie，并验证真实登录和退出行为。
- 发布前明确数据迁移、回滚或向前修复条件；不能把允许重新登录解释为允许丢弃持久业务数据。
- 新增登录及设置操作沿用现有页面组织和简体中文文案，不把这次改造扩展成整体界面重设计。

## Testing Decisions

### 主要测试边界

1. **HTTP 协议与应用行为**：通过实际 Worker 请求入口、Better Auth handler 和测试 D1 执行登录、设置、管理员、OAuth 及设备访问流程，验证响应、Cookie、后续访问结果和持久状态变化。对应协议约束尽量在这个入口拥有一个主测试，不靠私有函数调用次数或配置字符串判断功能成立。
2. **Worker RPC 契约**：通过现有 AuthService 对外方法及必要的本地 Service Binding 集成验证服务身份、操作范围、用户状态、权益、学校解绑与后台连续性。验证权限时使用真实鉴权与状态数据，不能把鉴权替换成始终允许的 mock；仅在学校外部系统、邮件发送等外部副作用处使用替身。
3. **浏览器交付验证**：补充 HTTP/RPC 测试无法证明的 host-only Cookie 隔离、登录回跳、单站退出不自动接回、Passkey 仪式和插件兼容性。它是对真实用户流程的验收，不要求为测试新增生产接口。

### 测试质量与现有基础

- 每个测试保护可观察行为或独立协议不变量，并有明确的可信回归场景。优先扩展共享 fixture、参数化案例及最高层现有测试，不在多层复制同一证明。
- 仓库已有 workerd 与测试 D1 基础，覆盖正式认证端点、稳定 issuer/discovery、PKCE 授权码兑换、OAuth 客户端管理、封禁后的 OAuth 行为和 QuickLogin 流程，可作为 HTTP 集成测试基础。
- 现有 RPC 客户端校验与采集错误边界测试可复用其环境构造和对外契约，但错误封装测试不能代替完整权限验证。
- 现有前端二次验证和登录继续流程测试可覆盖交互回归；WebAuthn 的自动化断言与真实浏览器验收分别记录，不能将按钮渲染或模拟回调当成真实 Passkey 验证。
- 原子性和多实例语义使用真实 workerd/D1 或匹配部署语义的测试环境验证，不以 JavaScript Map 或串行调用代替。时间边界可在测试环境控制；不为测试给生产增加专用开关。

### 必须通过的行为验收

- 无 KV 配置时，现有注册、登录、会话查询和数据保存正常，限流仍能拒绝超限请求；旧数据迁移后账号、学校绑定和权益保持。
- 并发兑换同一授权码、使用同一恢复码或提交同一 DPoP proof，最多产生一次合法成功；验证数据到期、限流并发行为和短期记录清理符合约定。
- 缺少 PKCE、错误 verifier、非 S256、错误回调、错误 issuer/audience 或超出范围的 token 被相应门禁拒绝，而不是被无关失败掩盖。
- 未绑定 Bearer 保持可用；已绑定 DPoP 在缺失 proof、错误 key/method/URL/ath、重放、refresh 换 key 或 Bearer 降级时被拒绝。
- 邮箱验证、密码找回、可信设备、角色变化与直接访问原生端点均不能跳过需要的 MFA 或近期认证。
- 没有 UV、错误账号、过期或重复 challenge 的 Passkey 不能建立强认证；合法多 Passkey 登录及五分钟内的再次验证流程可用。
- 普通会话不能添加或删除永久认证凭据；管理员只有密码、仅有角色或仅信任设备时不能使用管理功能，完成合法强认证后可按权限操作。
- 单站退出只影响本站；全设备退出、封禁和应用禁用对关联设备及刷新能力生效，即使漏收通知也满足六十秒上限；高风险请求检查最新状态。
- 正常改密、密码找回及人工恢复保留后台课表同步；人工重置成功后随机新密码可正常登录，旧密码、旧因子、信任设备、旧设备访问及未完成旧认证流程均不可继续使用，新密码明文不留在存储或日志；账号封禁和学校解绑拒绝相应后续 RPC 调用。
- 未获准服务、伪造客户端身份、被禁用应用、权限不足或不符合业务条件的目标用户被 RPC 拒绝；对外请求不能借任意 userId 绕入后台权限。
- CQU 邮件验证码、现有会话协调和后台取数流程不因 Auth MFA 调整而回归。

类型检查、协议文档一致性、针对性测试和整体验证分别记录；部署完成、自动测试通过及真实客户端验收是不同证据，不能互相替代。

## Out of Scope

- 本次不建设统一 API/MCP 平台、网关、工具、未来业务端点或开放应用注册平台。
- 不实施匿名动态注册、CIMD、PAR、个人 API token 平台或尚无当前需求的 OAuth 扩展；未来平台首期只读及管理员审批策略仅作约束记录。
- 不把私有 Worker 后台同步迁移成逐用户 refresh token，不新增平行的授权框架、服务注册表或统一客户端 SDK。
- 不强制现有客户端启用 DPoP，不建设独立 nonce 服务，不以 DPoP 替代用户强认证。
- 不新增完全无密码的注册模型，不强制普通用户启用 Passkey 或 MFA，不提供第一方授权的用户停用开关。
- 不为人工恢复建设额外审核工作流、受限恢复会话、强制因子重建或强制首次改密；采用管理员一次重置并生成随机新密码的方式。
- 不删除学校 CQU 邮件验证码链路，不重写学校登录容器或既有 Durable Object 业务状态机。
- 不更换全部业务 ORM，不引入 Redis 或新的通用认证缓存，不因框架升级自动改变稳定 issuer。
- 本次规格发布不等于实施、提交代码、合并或部署授权；实际构建和发布按后续任务执行。

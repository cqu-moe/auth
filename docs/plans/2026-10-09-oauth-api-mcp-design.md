# Auth 与第一方接入改进设计访谈

状态：已汇总已确认决策与推荐实施方案，待整体审阅。日期：2026-10-09。

正式规格：[GitHub Issue #41](https://github.com/cqu-moe/auth/issues/41)。本文件保留设计讨论与依据，后续拆票以正式规格为准。

目标是改进现有 Auth，利用维护中的 Better Auth 与 OAuth 安全机制，优化第一方接入。API/MCP 只预留架构边界，当前不建设平台。源码与官方资料核查见 [设计依据](./2026-10-09-oauth-api-mcp-design-evidence.md)。

## 本次范围

- 设计 Better Auth 升级、Auth 存储简化、账号安全和凭据撤销机制。
- 本轮加入 Passkey，明确其与密码、现有二次验证、近期验证和账号恢复的关系。
- 设计第一方独立会话、默认授权以及设备登录与后台同步的生命周期。
- 为未来 API/MCP 保留清楚的客户端、用户、资源与权限概念，优先复用框架契约。
- API/MCP 网关、业务端点、工具实现、客户端适配、开放应用注册平台均不在本次范围；不提前加入占位代码或未使用的基础设施。已有 Auth API 仍属于本次改进对象。

- 取消邮箱验证码作为第二因子；邮箱验证与密码找回保留，不能用找回密码解除已有二次验证。

- [迁移可要求一次重新登录或插件重新连接，保留账号、学校绑定和业务权益](../adr/0007-migration-compatibility.md)。
- [明确升级 Better Auth，授权码流程使用 S256 PKCE，本轮加入可选 DPoP 支持，暂不强制现有客户端](../adr/0010-upgrade-and-oauth-token-protection.md)。
- 未来第三方应用首期由管理员注册、审批，按明确需求适配 MCP 客户端；当前只记录，不实施。
- 用户要求把设计做薄，审视 KV 等组件是否确有必要；优先减少存储和自建机制。

## 当前建议，未作为已接受决策

- 已核实 KV 没有独立业务缓存用途，建议移除，以 D1 承担 Auth 的权威会话与验证数据，限流采用框架支持的数据库路径并补表；先不引入替代缓存或通用撤销基础设施。切换须处理 KV 中尚未完成的验证流程，并核实目标版本并发语义。
- 以已发布的 RFC 9700 和适用扩展为安全基线。OAuth 2.1 仍是草案；按实际客户端需求选择 DPoP、CIMD、设备授权等功能。

## 推荐实施方案

以下是根据已确认目标收敛的技术方案；它是设计草案，不表示代码已经实现。

### 1. 保留三个明确的职责

- Auth 管理中央账号、交互登录、应用身份、OAuth 和敏感账号操作。
- 第一方应用的后端管理本站会话，并通过中央 OAuth/OIDC 登录；后台 Worker 经私有 RPC 调用所需 CQU 能力。
- 现有 CQU/QuickLogin 的会话协调继续使用已有模块和必要的 Durable Objects。本次不为普通认证另建协调服务、授权服务或缓存服务。

身份用途分开：用户 OAuth 证明此次交互代表哪个用户；RPC 服务身份证明哪个后台被允许执行哪些业务操作。复用现有 client 身份与权限配置，不创建平行的服务注册体系。

### 2. 以 D1 为 Auth 的权威存储，移除 KV

移除 withCloudflare 的 kv 注入及不再需要的绑定、类型和测试替身；会话和 verification 走 D1，保持会话 cookie cache 关闭。限流显式使用数据库存储并补表，不能只删 kv，也不能意外回退到实例内存限流。

不预先引入 Redis、DO 认证缓存、授权版本表或自建令牌黑名单。当前用户状态、应用状态、权益和绑定已经有权威数据；先复用它们。普通读取的 60 秒是撤销上限，不要求刻意缓存 60 秒。

依赖升级后的验证码、授权码消费和限流必须验证并发语义；不能把数据库存储直接等同于所有操作均原子化。KV 中未完成的验证流程可在切换时要求重新发起，持久账号与业务数据保留。

### 3. 升级框架，采用现有客户端真正需要的 OAuth 安全机制

以核查时的 Better Auth 1.7.7 为评估基线，同步后端、前端相关包和目标版 Passkey 插件，确认 Cloudflare 适配器兼容性。生成 schema 后审查并纳入项目 SQL 迁移，核对客户端字段和资源配置，不直接在生产执行未经审查的自动迁移。

保持现有 issuer 身份和签名密钥连续性。将旧 validAudiences 配置迁入目标版资源模型，为当前实际存在的能力声明资源；不提前创建未来 API/MCP 的资源、端点或业务 scope。

用户交互采用授权码与 S256 PKCE，严格校验 redirect URI、登录事务、issuer、audience 和用途；第一方的免同意只省略同意页，不跳过这些校验。客户端是否第一方、是否能保密、是否具有后台 RPC 权限分别判断，客户端不能自行提升信任或范围。

利用框架已有的授权码消费、refresh rotation/reuse 防护、撤销与 OIDC 退出能力，并覆盖必要回归。用户已明确要求本轮加入 DPoP；PAR、CIMD、匿名动态注册等没有当前需要的扩展先不接入。

DPoP 要同时覆盖 token 签发、refresh 绑定、客户端 proof 和资源服务器验证。现有只接受 Bearer 的公共认证中间件、QuickLogin 设备认证和本地 JWT 辅助函数需要按真实 Request 校验，不能仅替换一个开关。采用框架已有的请求验证接口，既检查 token 的 issuer/audience/scope，又检查 proof 与请求、令牌和密钥的绑定，拒绝重放和 Bearer 降级。

选择启用 DPoP 的客户端需要处理密钥保存、丢失后的重新登录，以及请求签名；本次不强制所有现有客户端迁移。Auth 端处理公开 URL 与内部路由重写的一致性、认证头脱敏。AS 与资源端都需要覆盖多 Worker 实例的原子重放记录，不能使用实例内 Map 作为唯一防线；优先复用框架 createDpopReplayStore 与 D1 verification 的原子占位机制。

DPoP 暂不强制：未绑定 Bearer 按正常策略接受，已绑定 token 必须验证 proof 并拒绝降级。私有 Worker RPC 不受此迁移影响。DPoP 的请求签名密钥独立于 Passkey，不要求用户每次调用都做指纹或 PIN 验证；客户端可使用标准 OAuth 实现接入，不另造统一客户端框架。服务端 nonce 挑战不是本轮要求，不为它另建服务。

### 4. 第一方 Web 通过中央登录建立本站会话

中央 Cookie 仅属于 auth.cqu.moe；各应用使用自己的 host-only、Secure、HttpOnly 会话 Cookie。优先在已有应用后端完成 OAuth 交换和会话管理，不单独部署一层 BFF Worker。浏览器不持有长期 refresh token。

中央站按实际需要维护可信来源，收紧通配信任；Cookie 写操作仍需来源或 CSRF 校验。所有第一方应用默认开放，无需用户开通或授权；管理员通过权益控制使用资格、功能和额度，不提供用户停用第一方授权的开关。

单站退出只结束本站会话，停留在已退出页面；全设备退出结束中央及各应用的设备访问。退出同步机制优先复用框架 OIDC 能力，配合应用自身会话验证，不能仅发送一次通知就宣称撤销成功。

这一变化需要现有第一方调用方配合。切换中央 Cookie 前先完成调用方清单与接入迁移，并清理旧根域 Cookie；允许一次重新登录，不允许在客户端尚未适配时直接破坏其登录。

### 5. 后台 RPC 保留服务身份，集中执行权限检查

现有 getCaps、getCquTicket、cquHarvest 等内部能力按各自用途检查调用方身份与获批操作。Auth 统一查询目标用户状态、实际所需业务权益和学校绑定；检查按方法语义执行，不因某个方法不需要学校绑定就给它增加无关门禁。

仅存在 Service Binding 或知道 userId 不等于获准调用。保留当前服务凭据验证，不新增公网上等价的服务身份代用户入口；用户可访问的 HTTP handler 不得无条件转发任意 userId 到后台 RPC。

需要收紧的是通用 harvest 等方法中目前留给调用方的权限责任，而不是把所有后台任务迁入 OAuth。现有调度、用户选择和业务数据流程继续复用；调用审计关联服务、目标用户和操作。

### 6. Passkey 与敏感操作共用明确的认证规则

Passkey 仪式只在中央认证站进行，固定 rpID/origin；通过官方插件管理凭据和协议校验。服务端额外强制确认 userVerified，注册配置和登录校验分别处理。

普通 Passkey 登录与当前会话的再次验证分开。后者的一次性 challenge 绑定当前用户、会话、用途和有效期，不能接受另一个账号的 Passkey，也不能以普通新会话或自动续期冒充强认证。

优先复用框架接口；仅为缺失的近期认证语义增加一个集中实现，避免在每个设置端点各写一套验证。证明在服务端保存，五分钟到期；按用户已具备的方式验证：UV Passkey，或密码与账号已启用的二次验证。没有开启二次验证的账号不被要求提供尚未绑定的因子。

改密、换邮箱、关闭/替换二次验证、恢复码管理，以及新增/删除 Passkey，统一经过敏感操作门禁。保留密码与现有注册流程，支持多个 Passkey。邮箱验证码用于邮箱验证和找回，不创建绕过二次验证的完整登录，也不再作为第二因子。

“取消邮箱第二因子”只针对 Auth 中央账号。`src/email-handler.ts` 与 `src/services/cqu-2fa/` 处理的学校 CQU 验证码仍属于学校登录链路，不能随之删除或绕过。

管理员和超级管理员的管理会话必须有实际强认证依据，不能仅凭角色或信任设备进入；未配置的管理员先完成自身安全设置。管理功能准入与敏感操作五分钟内再次验证分别判断，避免把普通管理页面浏览误做成不断重复验证，也避免普通登录被提升为敏感操作证明。

二次验证材料全部丢失时由具备对应权限、已完成强认证的管理员执行一次重置：旧密码、Passkey、TOTP、恢复码、信任设备、旧会话、设备凭据及未完成旧认证流程全部作废，生成随机新密码并一次性返回，供管理员交付用户。只保存哈希，日志不含新密码明文；成功响应须代表重置完整生效。

用户用新密码正常登录，再按需设置 Passkey 或二次验证；不增加受限恢复、强制重建因子或强制首次改密流程。管理员账号仍须满足进入管理功能的强认证要求。普通忘记密码不删除已有认证因子。

### 7. 按身份用途定义撤销，不影响后台同步

| 事件 | 设备与交互凭据 | 私有 RPC 后台同步 |
| --- | --- | --- |
| 单站退出 | 结束本站会话，其他站与中央登录保留 | 继续 |
| 退出全部设备 | 结束各设备会话，并使相关设备凭据无法继续访问或刷新 | 继续 |
| 正常改密 | 保留当前已验证会话，结束其他设备访问 | 继续 |
| 普通密码找回 | 推荐结束原设备会话和相关设备凭据；保留已有二次验证和 Passkey，恢复后重新登录 | 继续 |
| 人工账号恢复 | 作废旧密码、全部旧因子、信任设备和旧交互凭据；生成随机新密码，正常登录 | 继续 |
| 账号封禁 | 拒绝用户访问并撤销相关用户凭据 | 拒绝该用户后续调用 |
| 学校解绑 | 结束对应学校能力的访问，不等同于删除中央账号 | 停止对应同步 |
| 管理员禁用应用 | 拒绝该应用的访问 | 拒绝对应服务身份的调用 |

恢复事件的设备凭据撤销是推荐默认值，后台继续已获确认。设备的 offline_access 不能因为框架默认保留离线令牌而逃过“退出全部设备”；无需为保留后台同步给设备留下例外，因为后台已使用独立服务身份。

自包含 JWT 仅验签不足以证明未撤销。当前 Auth 的受保护入口复用框架的令牌状态检查并结合现有权威数据；普通读取保证最多 60 秒，高风险能力在请求时读取最新状态。API/MCP 的未来验证实现不在本次建设范围。

对于已接收的长任务，推荐在下一个可控制的执行点检查停止条件，并阻止停止后继续开始新工作；不承诺撤回已返回的数据或中断所有外部请求。具体检查点在现有任务实现中确定，不另建取消任务平台。

## 本次设计审阅补充的约束

1. **跨应用撤销闭环**：应用自己的会话必须能关联到可核查的中央登录或用户授权状态。退出通知用于加速，不作为唯一保证；即使漏收通知，已撤销的设备也不能超过约定时限继续访问。权威验证失败后不能无限期沿用旧的允许结果，高风险操作不因 Auth 暂时不可达而放行。
2. **信任设备与近期认证分开**：当前 `src/auth.ts:272` 配置了三十天信任设备，它不代表刚完成 TOTP 或 UV。不得用自动创建的新 session、记住设备或角色变化自动生成五分钟强认证证明。
3. **原生端点没有旁路**：业务页面增加验证不够，需覆盖对应 Better Auth 原生端点与应用封装端点；例如改邮箱、MFA 管理、Passkey 删除和管理员操作都不能被直接发请求绕过。优先在共同后端入口落实，不依赖按钮是否隐藏。
4. **D1 的原子性与数据生命周期**：验证授权码/恢复码单次消费、限流计数和 DPoP jti 并发重复；确认过期 challenge 和 proof 记录会被清理。用框架现成的数据库原语完成，缺少保证时修最小适配，不默认新增队列或缓存服务。
5. **人工恢复是一次完整重置**：新随机密码生效时，旧密码、旧因子、信任设备、旧设备凭据及未完成旧认证流程均须失效；管理员强认证和审计仍保留，不另建恢复工作流。学校绑定、业务权益和后台同步按已确认要求保留。

这些是设计约束与待验收项，不是本次新复现的漏洞。管理员重置的完整失效效果、客户端撤销实现和生产存储状态仍需实施阶段核实。

## 交付顺序与验证

1. 固定目标版本和现有调用方清单，审查 schema、客户端数据与兼容性；先明确迁移和回滚条件。
2. 升级 Auth 与适配器，迁移 D1 表和限流，移除 KV；处理现有邮箱验证自动登录及第二因子路径。
3. 集中实现近期认证与 Passkey，收紧 RPC 权限检查，落实设备撤销与后台继续的边界。
4. 完成第一方后端接入与会话迁移，再切换中央 Cookie 和退出流程；更新接入文档及受影响契约。
5. 完成针对性自动验证与浏览器验收后，再讨论提交、部署等实际执行；本次仅设计。

核心验收包括：无 KV 时登录与限流有效；授权码并发消费不重复成功，缺失或错误 PKCE 被拒；DPoP 的错误密钥、缺失 proof、错误方法/URL/令牌哈希、重放和 Bearer 降级被拒，刷新保持密钥绑定；邮箱验证或找回不能绕过二次验证；未完成 UV 或错误账号的 Passkey 不能获得强认证；普通会话不能添加永久登录凭据；单站退出和全设备退出符合约定；设备失效后后台仍继续；封禁/解绑后 RPC 被拒；权限不足的服务或错误资源 token 被拒；现有账号、学校绑定与权益在迁移后保持。

## 11.2 跨站接续验收

在本地集成/测试环境，用测试账号或模拟真实API响应验证。任何需要真实学校账号的操作使用用户已有授权；不从磁盘搜凭据、不发送真实邮件到他人、不自动改真实学校密保邮箱。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 新用户从首页开始 | Auth内注册/验证/绑定完成前没有返回Schedule |
| 已登录未绑定 | 直接绑定，不进账号设置 |
| 邮箱未验证 | 验证完成后仍到绑定，不直接跳课表 |
| 启用2FA | 验证通过后继续绑定；验证码错误不能绕过 |
| 邮箱跨标签 | 原页面focus更新会话，恢复同一绑定目标 |
| 重置密码 | 重置后登录目标仍是绑定路由 |
| 老用户有凭证无邮箱行 | 不重复绑定，回原服务 |
| 刷新绑定中页面 | 恢复可继续步骤或查询真实处理中状态，无提前成功 |
| 首次登录失败/网络错误 | 原位错误重试；不显示成功、不开3秒跳转 |
| 新绑定成功 | 显示固定成功文案；3秒回Schedule，可立即返回/留在此页 |
| 独立账号中心入口 | 无自动课表跳转，有明确服务链接 |
| 非法/循环returnTo | 被拒绝或安全兜底，无站外任意跳转/循环 |

浏览器证据记录路径顺序即可，不记录完整带token的URL、Cookie或验证码。

## 11.3 初始化与同步验收

| 场景 | 必须观察到的结果 |
| --- | --- |
| 有权限、无记录、无订阅 | 一次事务三订阅/三链接/一个setup |
| 无sync权限 | 正常返回、零初始化写入、无新增开通流程 |
| 额度小于3 | 显示真实额度错误，不半建、不修改权益 |
| 刷新/双标签/重复请求 | 三条不重复、链接token不变 |
| 已有订阅 | 不无差别补齐，不改原订阅 |
| 删除部分或全部后重进 | 不恢复用户删除内容 |
| Queue发送失败 | 订阅存在，dispatch失败可恢复，没有假同步成功 |
| 发送与记录之间中断 | 租约到期后可恢复，可能重复消息有终态保护 |
| 正常首次同步 | 一条initial消息、共同runId，现有抓取写入三个视图 |
| 消费者失去权限 | 不抓取，保留原权限契约 |
| 旧run晚到 | 不覆盖新run结果 |
| 同步失败重试 | 走已有syncs，遵守额度/冷却，不重新创建订阅 |
| 返回空课表 | 显示真实同步完成，链接可用，不生成假课程 |
| 老数据后台同步 | 旧有效链接仍可复制 |

附加持久性验证必须重新建页面/客户端，而不是只在同一个JS内存实例重复调用。D1表中setup持久存在才算账号级防重复。

- [ ] 先运行 `verify-reference.py`，确认参考完整。
- [ ] 用确定的演示fixture把生产Dashboard置为同步中、成功、失败，分别截1280×960和390×844；与冻结截图/预览比对。

预览中的占位弹窗不是生产实现标准。按钮必须连接既有真实处理器。不得为了视觉一致把真实动态数据写死为3/10或“刚刚同步”。

## 11.5 发布边界与交付

本次任务只有计划授权。执行者得到实施指令后完成本地开发与验收；没有发布授权时止于此，不自动push。

后续明确发布时的兼容顺序：
1. Auth兼容性修复和绑定接续先上线（旧Schedule入口仍可用）。
2. Schedule先应用新增D1迁移，再发布依赖本表的后端与前端。
3. 两仓各自检查Git身份、精确暂存、commit并push，按现有Cloudflare Git Connector完成；不再额外手工wrangler deploy。
4. 验证生产版本、已部署静态资源、真实新用户动线。HTTP200/健康检查不能代替绑定与订阅成功。
5. 回退前端可保留新增setup表，避免丢防重复记录；不删除用户订阅或迁移生产数据来“回退”。

本地交付格式：
```text
AUTH：分支、提交SHA、测试结果、剩余问题。
SCHEDULE：分支、提交SHA、迁移文件、测试结果、剩余问题。
设计：冻结包校验结果、桌面/手机截图位置。
真实动线：已实测的步骤；需要用户账号或发布后才能验证的步骤。
发布：未执行 / 用户明确授权后的实际状态。
```

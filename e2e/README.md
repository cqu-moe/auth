# Local built Auth lifecycle

AUTH-01 / https://github.com/cqu-moe/auth/issues/79, AUTH-02 / https://github.com/cqu-moe/auth/issues/80, and workspace ticket AUTH-05. These are deterministic PR tests, not production or school acceptance.

## Run

Use Node 22.22.3 and the existing frontend pnpm 11.19.0 lockfile. Install root dependencies with `npm ci`, frontend dependencies with `pnpm --dir frontend install --frozen-lockfile`, and the pinned engine browser with `npx --no-install e2e-web install chromium` (CI adds `--with-deps`).

Run `npm run test:e2e`. It typechecks the tests, builds the real SPA with browser telemetry disabled, then uses the actual Worker entry bundled by Wrangler in a separate build-only configuration. It never reads a developer `.dev.vars` or starts a production binding. Miniflare/workerd uses the repository's original runtime version, real D1 and all repository SQL migrations. Assets are the built SPA served by Miniflare's assets service. CQU/QuickLogin DO classes are registered but their school, container and Workflow behavior is **not** covered by this ticket.

Each invocation runs desktop and 390×844 independently and executes every test the framework discovers (currently seventeen: two AUTH-01, six AUTH-02 and nine AUTH-05 journeys). Before starting a runtime, `e2e list --reporter json` supplies the actual IDs and complete title paths; exact title selection plus ID-set equality prevents a source-regex inventory from silently omitting quoted, multiline, describe-level, or table-driven declarations. AUTH-01 keeps its registration journeys in one fresh Worker/D1/browser runtime; each other discovered journey receives its own fresh loopback port, SQLite directory, browser context and test-process control server. This preserves the production authentication rate limit instead of raising or bypassing it while preventing unrelated journeys from consuming one another's 60-second window. The application origin is `localhost` on that isolated port: WebAuthn RP IDs are registrable domains, while an IP-address origin makes Chromium reject even a virtual-authenticator ceremony. Workers may call only the captured Resend email endpoint; browser requests may only use the current Auth origin. Unexpected egress is denied and fails the invocation. No actual message, school request or AI/model call is made. Both framework `E2E_TELEMETRY_DISABLED=1` / `DO_NOT_TRACK=1` and Wrangler telemetry opt-out are explicit in the runner and CI; the browser build has no PostHog token.

AUTH-01 exercises real signup, required/optional invitation policy, invalid/expired/used invitations, duplicate signup, wrong verification code, verification, protected UI gating, allowed/malicious return targets, reload persistence, logout/401 and wrong-password rejection followed by successful login. AUTH-02 adds exclusive real identities for profile/current/new-email OTP updates, password recovery failure and reuse, TOTP/recovery-code enrollment and reuse rejection, CDP virtual WebAuthn login/step-up/cancelled ceremony, recent-auth/administrator-purpose expiry after real password and TOTP proofs, browser admin step-up, protected-operation authorization/denial, and renewal bypass rejection, and password/whole-device logout revocation. Fixture rows only prepare registration settings, invitations and one-time prerequisites; no user, verification result, recovery result or session is seeded. Email OTPs and reset links originate in the app and cross only the external mail delivery adapter, which records only the latest message per synthetic recipient.

AUTH-05 adds real administrator admission, role changes, ban/unban and self-ban protection, ordinary-admin versus superAdmin permissions, managed invitation/preset registration and revocation, persisted registration policy/default entitlements, per-user entitlement effects, actual account-DO quota preview/apply, and administrator session revocation with user-owner isolation. The OAuth-client editor is exercised through creation, reopen/edit, secret rotation and deletion; its effects are independently checked against the real provider's S256 authorization-code/token/userinfo and invalid-client/callback paths. The registered synthetic HTTPS callback is read from the protocol response without following it; this does not claim a downstream browser callback or extension-device chain (AUTH-04 owns those).

The manual-recovery journey uses a real UV Passkey administrator and a target with enrolled Passkey, TOTP, recovery codes, trust cookie, interactive session, native OAuth access/refresh credentials, pending authorization and an application-generated reset email. Both cancellation paths preserve access. The real management confirmation and admin-purpose Passkey verification produce the one-time password; it is held only in memory, masked in the active UI, cleared on close/reopen and registered with artifact scanning. Old credentials and pending flows are rejected; the new password preserves identity, role and granted capabilities, requires fresh administrator strong authentication, and can rebuild MFA. Replaying the old trust cookie after re-enrollment still requires the new factor. The complete journey can exceed the unchanged public session-read rate window: an explicit safe-GET expectation waits through actual 429s for at most 70 seconds. No rate row, session, proof or successful business state is seeded or reset.

Shared account/TOTP helpers preserve AUTH-02's negative enrollment check; AUTH-05 setup does not repeat that separate contract. e2e 0.21's URL-only response matcher cannot distinguish a background GET from a POST to the same resource (the first invitation probe captured HTTP 200 instead of the POST's 201). Only response capture uses the installed engine's public Playwright surface to filter method plus URL; all deterministic UI actions remain tester-army/e2e. No internal HTTP response is mocked.

The test-process control server exposes narrow privileged actions that are never served by the Worker: create an unused invitation, promote a synthetic account to superAdmin, mark an already-created reset token, purpose-bound proof, or session-long strong proof as expired, register additional artifact secrets, and perform a real HTTP password sign-in for the revocation journey. The real-session action returns real application cookies only in memory, registers their values for artifact scanning, and does not bypass or synthesize login. Controlled expiry avoids waiting five wall-clock minutes; it does not claim to test clock drift or a native browser cancellation UI.

WebAuthn uses Chromium CDP virtual authenticators with protocol-level user verification. Registration, discoverable login and email step-up traverse the actual browser and server protocol. e2e-web 0.15 exposes no ceremony-cancel API, and removing a disconnected virtual authenticator leaves the request pending, so the cancellation case starts the real login ceremony and navigates away to abort it, then asserts no usable session exists. Native biometric/PIN prompts and real hardware authenticators remain outside these tests.

`node e2e/self-check.mjs` deliberately breaks the registration and administrator-entry assertions in separate runs **before** filling secrets. Each inner command must exit 1 with exactly its intended assertion failure in both viewports and leave a screenshot/report. The outer self-check verifies the assertion identity, counts and cleanup; a startup or unrelated failure cannot satisfy it. After a Secret fill, e2e intentionally disables screenshots for the remainder of that attempt. We retain redacted step/screen text and logs for those failures rather than bypassing that protection. Negative-control output remains separate from normal output. `node e2e/account-smoke.mjs` verifies the downstream account API described below.

Every run retains aggregate `.e2e/run-<time>/{desktop,mobile}/discovery.json`, `report.json`, `runner.log`, and `runtime.json`, plus numbered per-runtime directories containing their own framework report, runner log and cleanup record. Aggregate group reports keep their path relative to that viewport directory. No retries are enabled. Zero tests, skipped/interrupted required cases, selected or executed ID sets that differ from framework discovery, egress, secret leakage in text artifacts, startup and cleanup failures fail the command. Runtime cleanup always attempts to write its record; a cleanup error is retained alongside the original run error rather than replacing it. Text-artifact scanning covers synthetic passwords, application OTPs, reset URLs, TOTP URIs, recovery codes and cookies; revealed TOTP/recovery text is also hidden while the real UI remains active. Cleanup stops workerd and the mail control server and removes the run's SQLite/bundle directory. Never publish a runtime DB or mail payload. Public CI uploads only `.e2e/` synthetic reports.

User title greps are applied during framework discovery. Group execution replaces them with that group's exact titles; the CLI treats repeated `--grep` options as alternatives, so forwarding a broader grep would break per-journey runtime isolation. Other execution options are retained.

## Downstream fixed-commit interface

Consumers must check out a specific Auth commit (the integration merge owner records the final ticket commit), install its lockfiles and build its frontend. Never track moving `main`. The API is ESM, run with this Auth checkout as the process working directory:

- `startAuth({ expectedCommit })` from `e2e/runtime.mjs` checks the exact current commit before creating state. It resolves only after the actual Worker, migrated DB, assets and external mail adapter are available.
- Returned `origin` is the real local Auth HTTP origin; configure the consuming application to use it. `controlOrigin` is a privileged **test-process-only** loopback mail/config adapter, never a browser or production endpoint. Do not proxy it through applications.
- `prepareAccount(runtime, { email, password, name })` from `e2e/prepare-account.mjs` accepts only synthetic `@example.test` identities, seeds an unused invitation, then performs real HTTP signup, consumes the actual app-generated mail OTP and verifies the account. It reads back the verified identity and returns `{ email, password, userId }`. It deliberately discards the preparation session; downstream must exercise real login/OAuth rather than inject a session or token. Do not print the returned password.
- `runtime.db` is the isolated D1 handle, only for legitimate prerequisite setup such as a consumer's OAuth registration; it must not seed the success being tested. OAuth client setup/complete cross-app grants are owned by later tickets, not claimed here.
- Always `await runtime.close()` in `finally`; errors are failures. It removes the database, stops local services and rejects unexpected Worker egress. Per-consumer browser isolation and egress blocking remain the consumer's responsibility.
- `AUTH_E2E_EXPECT_COMMIT` applies the same pin to the runner. `AUTH_E2E_OUTPUT` must be a child of `.e2e`; `AUTH_E2E_MOBILE=1` runs only the phone viewport. Default runner executes both with separate runtime state.

School binding, queue/recovery workflow, OAuth grant/revocation, TOTP/Passkey and live test accounts remain the other tickets' responsibilities. This helper does not claim they work. The official CI aggregate requires the new browser job as well as the original application/container jobs; remote CI results must be reported separately from local execution.

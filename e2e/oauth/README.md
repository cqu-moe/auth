# OAuth / device / background lifecycle

Run `npm run test:e2e:oauth`, then `node e2e/oauth/run.mjs` for a second independent desktop/mobile run. `node e2e/oauth/self-check.mjs` verifies deliberate pre-secret assertion failures in both viewports, a real engine endAttempt cleanup failure, zero selection, and wrong commit pin. Every inner failure must exit 1; the self-check succeeds only after checking the intended cause, screenshots/reports and resource cleanup. CI runs all three commands in its required OAuth job.

The fixed `e2e@0.21.0` / `@e2e-dev/web@0.15.0` engine drives the built SPA deterministically. Only method-filtered response observation and cross-origin navigation use its public Playwright surface, as in AUTH-05; no AI or internal HTTP response mock is used. Core account, enrollment and school-binding UI coverage stays with AUTH-01/02/03/05. Their real API helpers prepare verified synthetic identities, school bindings and a strongly admitted recovery administrator. Only client registration, entitlement and administrator-role prerequisites are seeded. No successful login, proof, code, token, school state or business response is seeded.

The loopback test OAuth consumer validates state, exchanges S256 codes at the real token endpoint, and stores credentials only in memory. Each protected course page checks fresh native introspection (session/user/client/expiry and current business caps), uses actual proof-bound userinfo, then requests the real AuthService school directory through AUTH-03's private caller. Plain Bearer clients retain actual userinfo access; they cannot borrow first-party business claims or register an official QuickLogin device even from an accepted synthetic extension origin. This is a test consumer, not a claim about any downstream product's implementation.

Two independent device logins and a third website login receive distinct session IDs. Website device-management UI revokes one; its resource and refresh fail, while the other reads the synthetic course and the website saves/reloads a profile change. Removing actual business entitlement leaves OAuth authority active while both client business and private background RPC reject; restoring entitlement restores course results. Invalid verifier/callback/scope/resource and code replay have independent protocol denials from genuine authorized sources. Refresh rotation returns new credentials, serves proof-bound resources, and rejects old refresh reuse. Reuse intentionally revokes that client refresh family, so it runs after all continued-refresh checks.

DPoP issuance without proof, resource proof absence/replay, Bearer downgrade and wrong/missing refresh proof all fail at the real provider. Wrong/missing refresh proof uses a live unconsumed refresh token, followed by same-key success. Reusing an AS proof on the newly rotated credential fails; a fresh proof then succeeds, followed by actual userinfo and business readback. Token type is the real issuance response, not inferred from configured client flags.

The lifecycle journey creates a new usable OAuth device before each password change, administrator recovery, and all-device logout. Each old device loses resource and refresh access, while the approved private RPC still obtains actual school courses. Ban ends active device and background access; unban restores private business. Unbind stops private business and the still-authenticated application's course page. The original Worker, D1, DO, Workflow and Docker browser all run; only school and email delivery are external fixtures. No actual account, developer secrets, production binding, user browser profile or OS keychain is used. Login retries occur only after an actual 429 and bounded Retry-After/X-Retry-After, without editing rate-limit state.

Each discovered journey gets separate Worker/D1/DO/Workflow/container/control resources, loopback ports and a headless temporary Chromium profile. Playwright launch diagnostics verify headless/basic-password-store/mock-keychain flags and profile disappearance; the Linux school Chromium wrapper explicitly uses the same safe flags. Failures preserve the first error and cleanup error. Successful runs require nonempty real recovery Workflows, complete cleanup outputs, no school credentials/address rows, no container Chrome/profile, and independent Docker object/image removal. The runner accepts only discovery greps; headed, AI and retry overrides are rejected.

Use `AUTH_E2E_EXPECT_COMMIT=<full SHA>` for exact clean-checkout pinning. Source fingerprints and bundle hashes distinguish working-copy probes from fixed-commit runs. Evidence is in `.e2e/oauth-*/{desktop,mobile}/`: discovery, aggregate report/runtime and per-journey framework traces, sanitized logs, protocol status/fingerprint records and cleanup. Dynamic tokens, code/state/verifier, proofs, cookies and recovered passwords are registered for text-artifact redaction/scanning. Screenshots stop after a Secret fill; deliberate pre-secret failures retain safe PNGs. Never upload runtime databases, mail bodies or inherited debug archives.

Chromium phone viewport is not a physical device. Linux remote CI, live school/mail/deployment and Firefox/WebKit are separate acceptance layers. AUTH-06 owns live acceptance; no product publish is performed here.

The runner also inspects every selected native attempt: cleanup must be `complete`, with no cleanup-phase secondary errors, in addition to summary/IDs/status/exit checks. The cleanup control delegates the real web engine teardown, then deliberately throws through the public engine SPI; it reproduces e2e 0.21 returning a passed body/exit 0 with failed attempt cleanup. The OAuth wrapper must exit 1 while independently removing its actual Worker/Docker/browser resources. The same artifact is checked with its cleanup label changed to complete to prove secondary errors cannot be hidden by that label. These controls test the runner's report boundary; they do not fake an Auth business response. Main and school runner cleanup guards belong to the registration CI ticket.
